Unitree RL GYM 项目讲解

从设计、训练框架到策略部署的完整代码导读

本文面向刚接触项目的读者，按“快速入门、深入原理、开发扩展、部署排错”的顺序说明 Unitree RL GYM 的设计思路、核心模块、PPO 训练实现、机器人环境扩展方法，以及从 Isaac Gym 训练到 Mujoco 和真机部署的对齐要点。

适合读者

第一次接触本仓库，想理解并修改训练/部署链路的人。

主要目标

看懂架构、训练现有任务、改造机器人、导出策略、定位部署问题。

核心框架

Isaac Gym、rsl_rl、Mujoco、unitree_sdk2_python。

聚焦范围

Python 训练和 Python 部署主链路，不展开 C++/LibTorch 示例。

1. 项目概览

Unitree RL GYM 是一个基于 legged_gym 思路改造的四足/人形机器人强化学习仓库。 它用 Isaac Gym 做大规模并行物理仿真，用随仓库携带的 rsl_rl 实现 PPO 训练， 用 TorchScript 导出策略，再把策略放到 Mujoco 或 Unitree 真机控制程序里运行。

支持对象

  • go2：四足机器人，直接使用 LeggedRobot 基类。
  • g1：人形机器人，使用 G1Robot 定制观测、相位和奖励。
  • h1：人形机器人，使用 H1Robot 定制人形步态逻辑。
  • h1_2：H1_2 人形机器人，结构与 G1/H1 类似。

核心思想

训练阶段的环境、观测、动作、奖励和控制频率，必须在部署阶段被严格复现。 Mujoco 和真机并不会重新训练策略，它们只加载导出的 .pt 策略， 然后按同样的观测顺序和缩放方式推理动作。

阶段 入口文件 输入 输出 关键风险

4. 源码阅读路线

新手不要从 PPO 算法文件开始读。更稳妥的路线是先看入口，再看注册，再看环境，再看算法，最后看部署如何复现训练时的输入输出。

  1. README_zh.md：理解仓库对外给出的 Train、Play、Sim2Sim、Sim2Real 工作流。
  2. legged_gym/scripts/train.py：确认训练入口只做三件事：创建环境、创建 Runner、调用 learn。
  3. legged_gym/envs/__init__.py：看任务名如何映射到环境类、环境配置和 PPO 配置。
  4. legged_gym/utils/task_registry.py：看命令行参数如何覆盖配置，环境和算法如何被实例化。
  5. legged_gym/envs/base/legged_robot.py：看 Isaac Gym 中单步环境如何计算动作、仿真、奖励、reset 和观测。
  6. legged_gym/envs/g1/g1_env.py 或 h1/h1_env.py：看人形机器人如何改写观测、相位和奖励。
  7. rsl_rl/rsl_rl/runners/on_policy_runner.py：看训练循环如何采样轨迹并调用 PPO 更新。
  8. rsl_rl/rsl_rl/algorithms/ppo.py：看 PPO 的 clipped objective、value loss、entropy 和 KL 调整。
  9. deploy/deploy_mujoco/deploy_mujoco.py：看部署侧如何手工拼出同样的观测向量。
  10. deploy/deploy_real/deploy_real.py：看真机侧如何从 LowState 读取状态，构造观测并发布 LowCmd。

5. 训练框架

训练入口 train.py 本身很薄，它把复杂性委托给 task_registry 和 OnPolicyRunner。 这是一种典型的注册表设计：命令行只传任务名，注册表根据任务名找到环境类和配置对象。

训练调用链

入口文件做了什么

def train(args):
    env, env_cfg = task_registry.make_env(name=args.task, args=args)
    ppo_runner, train_cfg = task_registry.make_alg_runner(env=env, name=args.task, args=args)
    ppo_runner.learn(num_learning_iterations=train_cfg.runner.max_iterations,
                     init_at_random_ep_len=True)

这一段代码对应三个动作：

  • make_env：找到任务类和配置，设置随机种子，解析 Isaac Gym 参数，创建向量化环境。
  • make_alg_runner：把 PPO 配置转成字典，创建 OnPolicyRunner，处理日志目录和 resume。
  • learn：进入采样和更新循环。

任务注册

legged_gym/envs/__init__.py 把任务名、环境类、环境配置和训练配置绑定在一起。 用户传入 --task=g1 时，注册表就能找到 G1Robot、G1RoughCfg 和 G1RoughCfgPPO。 

task_registry.register("go2", LeggedRobot, GO2RoughCfg(), GO2RoughCfgPPO())
task_registry.register("h1", H1Robot, H1RoughCfg(), H1RoughCfgPPO())
task_registry.register("h1_2", H1_2Robot, H1_2RoughCfg(), H1_2RoughCfgPPO())
task_registry.register("g1", G1Robot, G1RoughCfg(), G1RoughCfgPPO())

命令行覆盖配置

helpers.update_cfg_from_args 会把 --num_envs、--seed、--max_iterations、 --resume、--load_run、--checkpoint 等命令行参数写回配置对象。 所以同一个配置类既能作为默认值，也能被 CLI 快速覆盖。

6. 环境实现

环境的核心是 BaseTask -> LeggedRobot -> 具体机器人类。 BaseTask 定义 rsl_rl 需要的向量化环境接口， LeggedRobot 实现通用腿式机器人仿真逻辑，G1/H1/H1_2 再覆盖人形机器人特有的观测和奖励。

观测构造

基类 LeggedRobot.compute_observations 默认使用线速度、角速度、重力投影、速度命令、关节位置偏差、关节速度和上一帧动作。 人形机器人如 G1 会改为更适合部署的结构：角速度、重力投影、命令、关节位置、关节速度、上一帧动作和步态相位的 sin/cos。

字段 训练中的来源 部署侧对应 为什么重要
角速度 base_ang_vel * obs_scales.ang_vel IMU gyroscope 或 Mujoco qvel[3:6] 坐标系或缩放错会导致姿态控制异常。
重力投影 projected_gravity 由四元数计算 gravity orientation 决定策略对机体姿态的感知。
速度命令 commands[:, :3] * commands_scale 遥控器或 YAML 初始命令乘 cmd_scale 命令范围不同会让策略收到未见过的输入。
关节位置 (dof_pos - default_dof_pos) * dof_pos_scale (qj - default_angles) * dof_pos_scale 默认角必须和训练配置一致。
上一帧动作 self.actions 部署循环保存的 action 提供动作平滑和历史信息。
步态相位 sin(2*pi*phase), cos(...) 用控制计数和周期 0.8 计算 训练和部署周期不同会打乱左右脚节律。

奖励函数

LeggedRobot._prepare_reward_function 会扫描配置中非零的 rewards.scales， 然后动态绑定同名的 _reward_xxx 函数。也就是说，新增奖励通常需要两处同时修改： 在环境类中写 _reward_new_term，在配置类中添加 new_term = 权重。

奖励权重的常见误区

负奖励不是越多越好。若 only_positive_rewards=True，总奖励会被裁剪到非负， 早期过强的负项可能让策略缺少可学习信号。新增奖励时建议先看单项曲线，再看总回报。

7. 配置字段索引

项目大量使用 Python class 作为配置容器。它不是普通 YAML，但读法类似：外层 class 是配置组，内层 class 是子配置。 训练启动时会通过 class_to_dict 转成字典传给 rsl_rl。

LeggedRobotCfg 常用字段

字段组 关键字段 说明
env num_envs、num_observations、num_privileged_obs、num_actions 决定向量化环境规模和策略输入输出维度。部署侧 num_obs、num_actions 必须匹配导出的策略。
init_state pos、default_joint_angles 机器人初始高度和动作零点。部署 YAML 的 default_angles 应与之对应。
control stiffness、damping、action_scale、decimation 动作到目标关节角的映射和 PD 控制频率。Mujoco 的 simulation_dt * control_decimation 应对齐策略周期。
asset file、foot_name、terminate_after_contacts_on URDF 路径、足端索引、碰撞终止条件。
domain_rand randomize_friction、randomize_base_mass、push_robots 提升策略鲁棒性，但过强会增加训练难度。
rewards scales、base_height_target、tracking_sigma 决定优化目标，是训练效果最敏感的配置之一。
normalization obs_scales、clip_observations、clip_actions 观测和动作裁剪缩放。部署侧必须复现观测缩放。

LeggedRobotCfgPPO 常用字段

字段组 关键字段 说明
policy actor_hidden_dims、critic_hidden_dims、rnn_type、rnn_hidden_size 定义 Actor/Critic 网络。G1/H1 常用 ActorCriticRecurrent 和 LSTM。
algorithm clip_param、gamma、lam、desired_kl、learning_rate PPO 更新的核心超参数。
runner policy_class_name、num_steps_per_env、max_iterations、experiment_name 控制训练循环、日志目录和策略类型。

Mujoco YAML 与 Real YAML

Mujoco YAML

  • policy_path：TorchScript 策略路径。
  • xml_path：Mujoco 模型路径。
  • simulation_dt 和 control_decimation：共同决定策略控制周期。
  • kps、kds、default_angles：PD 控制和动作零点。
  • ang_vel_scale、dof_pos_scale、dof_vel_scale、cmd_scale：观测缩放。

Real YAML

  • control_dt：真机控制周期。
  • msg_type：hg 或 go，决定 DDS 消息类型。
  • imu_type：IMU 在 torso 或 pelvis，影响坐标变换。
  • leg_joint2motor_idx：策略动作维度到电机索引的映射。
  • max_cmd：遥控器输入映射到速度命令的最大范围。

8. PPO 深入笔记

本仓库的算法层来自 rsl_rl。训练循环在 OnPolicyRunner.learn 中， PPO 更新在 rsl_rl/rsl_rl/algorithms/ppo.py 中， 网络结构在 ActorCritic 和 ActorCriticRecurrent 中。

训练循环的张量流

变量 典型形状 含义 来源
obs [num_envs, num_obs] Actor 输入。 env.get_observations() 和 env.step()
critic_obs [num_envs, num_privileged_obs] 或 [num_envs, num_obs] Critic 输入，可包含特权信息。 privileged_obs 优先，否则使用 obs
actions [num_envs, num_actions] 策略采样动作。 PPO.act 调用 Actor 分布采样。
rewards [num_envs] 环境奖励。 env.step(actions)
dones [num_envs] 是否 reset。 碰撞、姿态或 episode 超时。
advantages [num_steps, num_envs, 1] 策略梯度使用的优势估计。 RolloutStorage.compute_returns

Actor-Critic

ActorCritic 中 Actor 输出动作均值，Critic 输出状态价值。 动作分布是对角高斯分布：均值来自 Actor，标准差 std 是可训练参数。 训练时用 distribution.sample() 采样动作，部署时用 act_inference 直接输出均值动作。 

mean = actor(observations)
distribution = Normal(mean, mean * 0.0 + std)
action = distribution.sample()
value = critic(critic_observations)

LSTM 记忆

G1 的配置中 policy_class_name = "ActorCriticRecurrent"， 并配置 rnn_type = "lstm"、rnn_hidden_size = 64。 Recurrent 版本会在 Actor 和 Critic 前各放一个 RNN 记忆模块。 采样时保存 hidden state，更新时用带 mask 的序列 batch 训练。

为什么部署时 LSTM 策略有状态

export_policy_as_jit 对 LSTM 策略会导出 PolicyExporterLSTM。 它在模块内部注册 hidden_state 和 cell_state buffer。 因此部署循环每次调用策略时，策略会保留上一时刻记忆。若需要重新开始一段 episode，应调用导出的 reset_memory。

GAE 与 Returns

PPO 需要优势函数 A_t。rsl_rl 在 RolloutStorage 中根据最后一个价值估计、奖励、done 和 timeout 信息计算 returns 和 advantages。 常见的 GAE 形式为： 

delta_t = r_t + gamma * V(s_{t+1}) * (1 - done_t) - V(s_t)
A_t = delta_t + gamma * lambda * (1 - done_t) * A_{t+1}
return_t = A_t + V(s_t)

其中 gamma 来自 algorithm.gamma，lambda 来自 algorithm.lam。 process_env_step 会对 time-out 做 bootstrap，避免因为 episode 达到最大长度而错误惩罚价值估计。

PPO clipped objective

代码中的核心比率是新旧策略下同一动作概率的比值：

ratio = exp(new_log_prob - old_log_prob)

策略损失使用 clipped surrogate：

L_policy = mean(max(-A * ratio,
                    -A * clamp(ratio, 1 - clip, 1 + clip)))

这里代码写成负号，是因为 PyTorch 优化器默认最小化 loss。 当新策略比旧策略变化太大时，clamp 会限制更新幅度，避免一次训练把策略推得太远。

Value loss、Entropy 和 KL 自适应学习率

  • value_loss：Critic 预测值和 return 的均方误差，可选择 clipped value loss。
  • entropy：鼓励探索，权重由 entropy_coef 控制。
  • desired_kl：若 KL 过大则降低学习率，过小则提高学习率。
loss = surrogate_loss + value_loss_coef * value_loss - entropy_coef * entropy

调参建议

若训练震荡明显，先看 KL、学习率、动作标准差和 reward 曲线。 若策略不动或动作很小，检查奖励是否过弱、entropy 是否太低、动作尺度是否太小。 若动作发散，检查终止条件、关节限位、PD 参数和观测缩放。

9. Play 与策略导出

play.py 是训练和部署之间的桥。它会创建一个更小、更稳定的测试环境， 加载 checkpoint，获取推理策略，然后导出 TorchScript。

Play 会覆盖哪些训练配置

  • num_envs 限制到最多 100，便于可视化。
  • 关闭地形 curriculum、观测噪声、摩擦随机化和 push。
  • 设置 env_cfg.env.test = True，使仿真按接近实时节奏播放。
  • 设置 train_cfg.runner.resume = True，从日志目录加载模型。

导出文件

策略类型 导出文件 适用场景
普通 MLP logs/<experiment>/exported/policies/policy_1.pt 无 RNN 记忆的策略。
LSTM / Recurrent logs/<experiment>/exported/policies/policy_lstm_1.pt G1/H1 等需要历史记忆的人形策略。

部署使用自己的训练模型

默认 YAML 可能指向 deploy/pre_train/<robot>/motion.pt。 如果要用自己训练的模型，需要把 YAML 里的 policy_path 改为 play.py 导出的策略文件路径。

10. 新增或改造机器人示例

新增机器人最容易出错的点不是某一个文件，而是训练侧和部署侧的多个配置必须一起改。 可以把 G1 或 Go2 当模板：四足优先参考 Go2，人形优先参考 G1/H1。

新增机器人流程图

以 G1 为模板的改造步骤

  1. 在 resources/robots/ 放入新机器人的 URDF 或 XML，并确认关节名称和连杆名称。
  2. 复制 legged_gym/envs/g1/ 或创建新目录，编写 new_robot_config.py 和可选的 new_robot_env.py。
  3. 在配置中设置 asset.file、asset.foot_name、terminate_after_contacts_on。
  4. 按 URDF 的关节顺序设置 init_state.default_joint_angles，确保和部署 YAML 的 default_angles 一致。
  5. 设置 control.stiffness、control.damping、control.action_scale 和 control.decimation。
  6. 设置 env.num_observations、env.num_privileged_obs、env.num_actions。
  7. 若使用自定义观测，改写 compute_observations，同时更新 _get_noise_scale_vec。
  8. 新增奖励函数时，添加 _reward_xxx，并在 rewards.scales.xxx 中给出非零权重。
  9. 在 legged_gym/envs/__init__.py 注册新任务名。
  10. 训练、Play 导出策略，再为 Mujoco 和真机准备部署 YAML。

新增机器人检查表

  • URDF 中关节名称能被配置中的 default_joint_angles 匹配。
  • 足端名称能被 foot_name 匹配，否则足端奖励和接触判断会错。
  • num_actions 等于策略控制的关节数。
  • num_observations 等于 compute_observations 拼接后的长度。
  • 训练配置、Mujoco YAML、Real YAML 的 action_scale、default_angles、观测缩放一致。
  • 真机 leg_joint2motor_idx 顺序和策略动作顺序一致。
  • 新增奖励项在 TensorBoard 中能看到合理数值范围。

11. Sim2Sim：Mujoco 部署

deploy_mujoco.py 的本质是一个手写控制循环： 加载 XML 和 TorchScript 策略，每个 Mujoco 小步都执行 PD 控制， 每隔 control_decimation 个仿真步拼一次观测并调用策略。

部署流程图

控制频率

以 G1 的 Mujoco YAML 为例，simulation_dt = 0.002，control_decimation = 10， 策略控制周期就是 0.002 * 10 = 0.02s，也就是 50Hz。 这应与训练侧 sim.dt * control.decimation 和真机 control_dt 对齐。

观测顺序

obs[:3] = omega
obs[3:6] = gravity_orientation
obs[6:9] = cmd * cmd_scale
obs[9 : 9 + num_actions] = qj
obs[9 + num_actions : 9 + 2 * num_actions] = dqj
obs[9 + 2 * num_actions : 9 + 3 * num_actions] = action
obs[9 + 3 * num_actions : 9 + 3 * num_actions + 2] = [sin_phase, cos_phase]

这段顺序必须和训练中的 G1Robot.compute_observations 一致。 如果你改了训练观测结构，却没有同步改部署代码，策略会把错误字段当成输入，表现通常会明显失控。

12. Sim2Real：Python 真机部署

真机部署在 deploy_real.py 中实现。它比 Mujoco 多了三件事： DDS 通信、遥控器状态机和安全过渡流程。 控制核心仍然是：读状态、构造观测、策略推理、动作映射、发布低层关节命令。

真机观测构造

真机侧从 low_state.motor_state 读取关节位置和速度，从 low_state.imu_state 读取四元数和角速度。 若 imu_type = "torso"，还会根据腰部关节把 IMU 数据转换到 pelvis 坐标系。 

cmd[0] = remote_controller.ly
cmd[1] = remote_controller.lx * -1
cmd[2] = remote_controller.rx * -1

target_dof_pos = default_angles + action * action_scale
low_cmd.motor_cmd[motor_idx].q = target_dof_pos[i]
low_cmd.motor_cmd[motor_idx].kp = kps[i]
low_cmd.motor_cmd[motor_idx].kd = kds[i]

真机部署的核心风险

真机部署没有仿真 reset 保护。若关节映射、默认角、IMU 坐标、动作尺度或 PD 增益错了， 策略可能立即输出危险动作。首次上机应降低速度命令、确认零力矩和急停流程，并先在架空或安全支撑条件下测试。

13. 对齐与排错

训练、Mujoco、真机三者要对齐的是“策略看到的输入”和“动作产生的物理效果”。 策略文件本身只是一个函数，若输入含义变了，它不会知道。

训练效果差

现象 优先检查 说明
机器人很快摔倒 终止条件、初始姿态、PD 参数、base height 奖励 先确保初始姿态稳定，再调奖励。
动作几乎不动 action_scale、entropy、奖励正向信号 动作尺度太小或探索不足会学成保守策略。
回报震荡 KL、学习率、随机化强度 自适应学习率频繁变化可能说明更新过激。
走路姿态奇怪 相位奖励、足端接触、关节惩罚 人形机器人尤其依赖相位和足端接触奖励。

Sim2Sim 不一致

  • 逐项打印训练观测和 Mujoco 观测的均值、范围，确认字段顺序一致。
  • 检查 default_angles 和训练配置中的 default_joint_angles 是否按同一关节顺序排列。
  • 检查 action_scale 是否一致，目标角计算是否都是 default + action * scale。
  • 检查 simulation_dt * control_decimation 是否等于训练策略周期。
  • 检查 XML 的关节轴、惯量、碰撞体是否和训练 URDF 差异过大。

Sim2Real 异常

  • 若收不到状态，先检查网卡名、机器人网络、DDS 初始化和 topic 名。
  • 若关节方向不对，优先检查 leg_joint2motor_idx 和默认角顺序。
  • 若姿态反馈异常，检查 imu_type 和 transform_imu_data 是否匹配机器人安装位置。
  • 若动作过大，先把遥控器命令范围降到很小，再检查 action_scale 和 PD 增益。

14. 真机安全清单

真机上机前建议按下面清单逐项确认。任何一项不确定，都应先回到 Mujoco 或低增益测试。

软件和网络

  • 确认网卡名和运行命令中的 net 参数一致。
  • 确认 lowcmd_topic 和 lowstate_topic 与机器人模式匹配。
  • 确认 policy_path 指向正确导出的 TorchScript 文件。
  • 确认策略类型是 MLP 还是 LSTM，必要时能重置 LSTM 记忆。

机器人配置

  • 确认 leg_joint2motor_idx 与真实电机顺序一致。
  • 确认 default_angles 是机器人安全站立姿态。
  • 确认 kps、kds 不高于安全测试范围。
  • 确认 imu_type 与机器人 IMU 安装位置一致。

操作流程

  • 先进入零力矩状态，确认遥控器 Start 逻辑正常。
  • 默认姿态插值过程中观察关节是否按预期方向运动。
  • 进入策略前，把遥控器速度命令保持在零或极小范围。
  • 确认 Select、Ctrl-C 或外部急停流程可用。

首次闭环

  • 优先在安全支撑或架空条件下测试。
  • 先短时间闭环，观察关节目标角是否平滑。
  • 逐步增加速度命令，不要直接给最大命令。
  • 记录异常时刻的观测、动作和 LowState，用于回放排错。

15. FAQ

为什么训练能走，Mujoco 里却很差？

最常见原因是部署观测和训练观测不一致，其次是控制频率、动作尺度、默认关节角和模型动力学差异。 先不要调 PPO，先逐项对齐部署 YAML 和训练配置。

修改观测后需要改哪些地方？

至少要改训练环境的 compute_observations、env.num_observations、噪声向量 _get_noise_scale_vec， 以及 Mujoco/真机部署里的观测拼接代码和 YAML 的 num_obs。

为什么 G1 的 num_observations 是 47？

G1 观测通常由 3 维角速度、3 维重力投影、3 维命令、12 维关节位置、12 维关节速度、12 维上一帧动作、2 维相位组成， 合计 3 + 3 + 3 + 12 + 12 + 12 + 2 = 47。

为什么 privileged observation 比普通 observation 多？

privileged observation 只给 Critic 使用，可以包含部署时不容易获得的信息，例如基座线速度。 Actor 部署时只能用普通 observation，因此普通 observation 必须能在真机侧获得。

新增奖励函数后没有生效怎么办？

检查函数名是否是 _reward_xxx，配置中是否存在 rewards.scales.xxx 且权重非零。 权重为零的奖励不会被加入 reward function 列表。

该先调训练还是先调部署？

如果 Isaac Gym Play 本身效果不好，先调训练。如果 Play 正常但 Mujoco 或真机异常，优先查观测、动作和控制频率对齐。

本文为什么不展开 C++ 部署？

本文聚焦 Python 训练、Mujoco 部署和 Python 真机部署主链路。 C++/LibTorch 示例属于另一条部署路径，策略文件和观测对齐原则相同，但构建和运行细节不同。
